## ЖЁСТКИЕ ОГРАНИЧЕНИЯ (не нарушать никогда)

1. `TRADING_DISABLED=True` — константа в конфиге; торговый конвейер при старте проверяет её и отказывается отправлять ордера, если True. Любая отправка ордера проходит через единственную точку — `ExecutionRouter.submit()`, которая при TRADING_DISABLED пишет в лог и возвращает simulated fill. Никаких обходов.
2. Никаких реальных API-ключей в коде/логах/отчётах. Секреты — только из `.env` (в .gitignore) через `src/bot/config.py::SecretsProvider`, который падает при отсутствии переменных окружения. Демо-ключи допустимы только локально и никогда не коммитятся.
3. Не ломать существующие модули Trade3 (src/trading_engine/*, research/*) — бот отдельное приложение, которое импортирует их как библиотеки.
4. Не удалять и не переписывать исследовательскую историю research/multi_exchange/.
5. Новые пакеты — только в .venv и только при отсутствии обходного пути (фиксируй обоснование).
6. Git-коммиты разрешены (исследование+код), push — только с отдельного разрешения пользователя.
7. Соблюдать trade3-research-protocol для любых новых гипотез: регистрация до результатов, хеши датасетов, CONSUMED-периоды не трогать.

## ПОСЛЕДОВАТЕЛЬНОСТЬ РЕАЛИЗАЦИИ (строго по этапам, каждый — критерии готовности перед следующим)

### Этап 1. Каркас приложения
- Создать `src/bot/` (app.py, config.py, secrets.py, clock.py — инъекция времени; logging). Конфиг: TRADING_DISABLED=True default.
- Готовность: `python -m src.bot.app --selftest` проходит; конфиг валидируется.

### Этап 2. Venue-адаптеры (порядок: Bybit → OKX → KuCoin → HTX → BingX → WEEX)
- Наследники `trading_engine.exchange.base.Exchange` + WS-подписки по образцу `collectors/ws_recorder.py` (топики Bybit: allLiquidation., orderbook.50. — НЕ liquidation./orderbook50.).
- Для каждого адаптера: нормализация таймстемпов в UTC ms, retry/backoff, rate-limit-регулятор per-endpoint (веса из доков), ping/pong, детектор sequence-гэпов.
- Демо-поддержка: OKX (`x-simulated-trading: 1`), BingX (open-api-vst.bingx.com), Bybit (demo trading). HTX/WEEX — только paper-режим.
- Готовность: для каждой биржи integration-тест read-only (публичные данные): свечи, funding, OI при наличии; синхронность меток с Bybit в пределах допуска; 0 ошибок нормализации на 10k сообщений.

### Этап 3. Сбор и хранение
- Расширить ws_recorder до всех 6 бирж (фunding-тикеры, ликвидации где есть, стакан snapshot+инкременты); хранилище raw (JSONL) + normalized (parquet/CSV) с контент-хешами; QC-пайплайн (trading_engine.data.quality) обязателен перед использованием.
- Готовность: 24ч непрерывной записи без потери sequence ≥ 99.9%.

### Этап 4. Strategy-runtime
- Единый интерфейс стратегии (on_bar/on_tick/on_funding → Signal), изоляция модулей (исключение в одной стратегии не убивает остальные), hot-enable/disable, per-strategy лимиты.
- Готовность: демо-стратегия (например, пересечение EMA — заведомо не для продакшена) проходит paper-цикл end-to-end на 5 днях записанных данных.

### Этап 5. Portfolio Risk Manager
- По BOT_BLUEPRINT/RISK_MANAGER.md: лимиты per-strategy/per-venue/per-symbol/portfolio; counterparty-лимиты (остаток на WEEX/BingX ≤ порога из конфига); margin-модель delta-neutral пар; kill-switch (portfolio DD, reconciliation mismatch > N, venue-latency > M).
- Готовность: тесты на синтетических сценариях (каждый лимит срабатывает; kill-switch гасит все стратегии).

### Этап 6. Execution Router
- Идемпотентность (client order id = hash(strategy, signal, bar)), защита от повторной отправки, partial fills, reconciliation loop (позиции/ордера/balance после каждого цикла), маршрутизация по лучшей цене (только симуляция до разрешения на торговлю).
- Готовность: детерминированные тесты из docs/VALIDATION_PROTOCOL.md (Backtest Correctness Requirements) — все 14 пунктов.

### Этап 7. Мониторинг и эксплуатация
- Логи структурированные, метрики (Prometheus-формат), алерты (Telegram/webhook — без секретов в репо), аварийное отключение, восстановление состояния после перезапуска (journal replay).
- Готовность: kill -9 → рестарт → состояние позиций/ордеров восстановлено из journal, расхождений нет.

### Этап 8. Paper-этап (минимум 30 дней, ≥20 сделок на стратегию)
- Только стратегии, прошедшие исследовательские критерии. На момент старта — их нет; бот копит prospective-данные (funding carry, ликвидации) для будущих HYP-M-003/004. Paper-прогоны разрешены на записанных данных, но без права на «подтверждение» гипотез — только инфраструктурная проверка.
- Готовность: reconciliation backtest-vs-paper на исполнении ≤ заявленного slippage-моделирования.

- Bybit demo / OKX simulated / BingX VST. Сравнение исполнения vs paper. HTX/WEEX — вне demo.
